# Flow windows and accounting

A flow detail identifies an ordered IPv4 TCP or UDP tuple within one collection window. Both TCX hooks can update that tuple. Each window has a configurable fixed capacity. A tuple that sends again in a new window has a new identity. Within a window, the same tuple can cover multiple connections or datagrams. Last seen is based on monotonic kernel time and converted to wall time for display. The observation span measures time between the first retained packet and last recorded activity.

A lifetime hash eventually fills even if the live working set is small. Expiring entries by TTL from userspace would race with packet updates between the check and deletion, and a tuple could be reused before deletion. LRU keeps admitting new tuples but can evict entries before their observations have been exported. Argus rotates whole generations of ordinary hash maps to bound tuple retention and obtain a stable walk. A single-entry map-of-maps points both TCX hooks at the active hash. Replacing the pointer from userspace waits for in-flight readers of the previous map. The collector owns the sealed map through the walk and releases it on completion. The old and new hash tables can coexist during rotation. Each has the configured capacity.

A window lasts approximately one collection interval. Flows remain visible in the most recently published window until the next successful publication. A failed walk leaves the previous snapshot visible with its original collection time. The failed sealed generation is counted once and released. Burst traffic can fill one window before the next rotation, so a busy tuple can keep accumulating detail while later new tuples may miss admission. Flow detail and application classification are best-effort.

Fixed-cardinality per-CPU counters record eligible observations independently of detail admission. Counts are cumulative for the loaded TCX program's lifetime. Bytes use the socket buffer length and packets count hook invocations for supported traffic. Unsupported frames, malformed headers, detail admission failures, and observation accounting failures have separate metrics. Receiver loss requires a receiver measurement.

The transport-only counters feed both Prometheus and API rate history. Subsequent observations can promote a tuple's application label inside a window. Legacy L7 counters add each successful window once, using its final label. A new classification never transfers bytes already published under another label. A new window starts with fresh classification evidence. Its detail totals can omit full-window failures and observations that could not be retained.
